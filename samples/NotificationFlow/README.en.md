# Complete notification rendering flow

[Русский](README.md)

This sample stores aliases and a message template in SQL Server, finds the template by code, passes a customer ID to TemplateEngine, and renders the message using an actual SQL query generated by SqlServerQueryGenerator. There is no fake data provider.

## Run

Requires .NET 10 SDK and SQL Server. On Windows the default connection uses an installed MSSQLLocalDB instance and tempdb.

From the repository root:

```powershell
dotnet run --project samples/NotificationFlow
```

For another test database, set the DEVELKIT_SAMPLE_SQL environment variable to its connection string. The connection needs permission to create schemas and tables. Use a dedicated test database and keep credentials out of source code.

Each run creates a unique notification_demo_<guid> schema inside a transaction. The finally block rolls the transaction back, including all schema, table, and data changes. Templates and customers are stored in SQL for the duration of the demonstration.

## Flow

1. NotificationCatalog creates the parameters, templates, fieldMetadata, and person tables.
2. An administrator saves two aliases and their technical expressions.
3. A message author saves a template under the meeting-reminder code.
4. NotificationService loads the template and aliases.
5. TemplateEngine expands aliases, parses the template, and builds a query filtered by customer ID.
6. PreparingTemplateDataProvider loads metadata and adds an offset column. SqlServerTemplateDataProvider calls SqlServerQueryGenerator.Generate, creates and executes a parameterized command, and reads the result columns.
7. The decorator converts types and UTC dates. The engine maps columns to nodes, then the formatter evaluates conditions and renders each message.

Program.cs verifies two customers with different UTC offsets, both if branches after converting SQL bigint to Int32, literal SQL-like text, an unknown template, and an unknown customer. A failed check produces a nonzero exit code.

## Scope

The catalog and notification service belong to the application. The library does not prescribe template persistence or lookup. For brevity, a single appointment date is stored on person. See samples/Meetings for relationships.

The provider borrows an open connection and transaction for sequential use. Production code must define connection lifetimes, concurrency, permissions, template versioning, and recipient selection. This sample renders text only: delivery, SMS pricing, transliteration, and HTML encoding are outside its scope.
